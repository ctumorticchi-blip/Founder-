## §0. Constat validé par l'inspection

Lecture intégrale de `src/engine/economic-models/{service,hospitality,retail,agency,subscription}.ts`
et de `src/engine/simulation/businessResolution.ts` (les 5 blocs de résolution
par famille, déjà réécrits en M11.2.3.1 pour construire `totalDemand = newDemand + repeatDemand`).

Constat confirmé, famille par famille :

**Service** (`computeServiceMonth`) :
```ts
const demandCap = Math.min(decisions.targetHours, decisions.capacityHours);
const baseUtilization = BASE_UTILIZATION + state.reputationScore * REPUTATION_UTILIZATION_BONUS; // 0.5 + rep*0.4
const noise = ctx.rng.nextGaussian(0, UTILIZATION_NOISE_STD_DEV);
const utilizationRate = clamp(baseUtilization + noise, 0, 1);
const hoursSold = demandCap * utilizationRate;
```
`demandCap` (= `min(totalDemand, capacity)`, déjà la vraie demande captée
depuis M11.2.3.1) est encore multiplié par un `utilizationRate` aléatoire
(0.5-0.9 selon réputation, ± bruit gaussien). Une demande déjà captée peut
donc disparaître une seconde fois ici, sans rapport avec la capacité
physique.

**Hospitality** (`computeHospitalityMonth`) : structure rigoureusement
identique, `fillRate = BASE_FILL_RATE(0.45) + reputationScore*0.4 + bruit`.

**Agency** (`computeAgencyMonth`) : structure identique,
`winRate = BASE_WIN_RATE(0.3) + reputationScore*0.25 + skillFactor*0.25 + bruit`.

**Retail** (`computeRetailMonth`, alias `RetailEngine.computeMonth`) —
structure DIFFÉRENTE, bug distinct mais de même nature :
```ts
const baseConversion = BASE_CONVERSION_RATE(0.2) + state.reputationScore * 0.3;
const noise = ctx.rng.nextGaussian(0, CONVERSION_NOISE_STD_DEV);
const conversionRate = clamp(baseConversion + noise, 0, 1);
const demand = decisions.expectedFootTraffic * conversionRate;   // ré-interprète totalDemand comme du "trafic" brut
const unitsSold = Math.min(demand, decisions.stockUnits);
```
Ici, `businessResolution.ts` passe déjà `totalDemand` (nombre de clients qui
veulent réellement acheter, calculé par `computeOfferDemand`+`computeRepeatDemand`)
dans `decisions.expectedFootTraffic`. Le moteur Retail traite pourtant ce
nombre comme une simple fréquentation à reconvertir une seconde fois via
son propre `conversionRate` (réputation + bruit), AVANT même de comparer au
stock. Une demande déjà captée par le Demand Engine est donc rétrécie une
deuxième fois avant d'être comparée à la contrainte physique réelle
(`stockUnits`). C'est la même famille de bug que Service/Hospitality/Agency,
sous une forme légèrement différente (la seconde conversion précède la
comparaison à la capacité au lieu de la suivre).

**Subscription** (`computeSubscriptionMonth`) — AUCUN double comptage
trouvé : `decisions.newSubscribers` (= `funnel.demand`, transmis tel quel
par `businessResolution.ts`, ligne `totalNewSubscribers += funnel.demand`)
alimente directement `endingSubscribers = activeSubscribers - churned +
newSubscribers`, sans second filtre. Le seul RNG de ce moteur porte sur
`churnRate` (résiliation), un phénomène réellement incertain et distinct de
« combien de la demande captée devient une vente » — conforme à l'énoncé
§8/§10 (RNG légitime hors du chemin demande captée → vente). **Aucune
modification requise dans `subscription.ts`.**

**Capacité physique réelle (à ne jamais retirer)**, déjà branchée dans
`businessResolution.ts` et indépendante des taux de conversion ci-dessus :
- Service : `remainingCapacityHours` (heures fondateur + effectif).
- Hospitality : `remainingCoversCapacity` (heures / `LABOR_HOURS_PER_COVER`).
- Retail : `remainingCapacityUnits = min(stockUnits, laborCapacityUnits)` — stock ET main-d'œuvre, déjà deux contraintes réelles combinées.
- Agency : `remainingCapacityMandates` (heures / `LABOR_HOURS_PER_MANDATE`).
- Ces capacités ne sont PAS concernées par ce jalon : seule la conversion
  demande captée → vente à l'intérieur de chaque moteur économique change.

`lostToCapacity = max(0, totalDemand - capacityForOffer)` dans
`businessResolution.ts` ne dépend JAMAIS de `contribution.sales` (déjà vrai
avant ce jalon, vérifié à la lecture) — donc les valeurs de
`lostToCapacity` déjà testées/calibrées en M11.2.3.1 restent valides
après ce nettoyage ; seul `contribution.hoursSold/coversServed/unitsSold/wonMandates`
(donc `sales`) change de valeur (augmente, devient exact plutôt que
statistiquement inférieur à `min(totalDemand, capacity)`).

**Diagnostic confirmé, STOP non déclenché : on implémente.**

## §1. Frontière architecturale cible

```
Demand Engine    (computeOfferDemand + computeRepeatDemand, M11.2.2/M11.2.3.1, INCHANGÉS)
      -> décide COMBIEN veulent acheter (totalDemand)
Capacity         (calcul par famille dans businessResolution.ts, INCHANGÉ)
      -> décide COMBIEN peuvent être servis (capacityForOffer)
Economic Engine  (computeXMonth, MODIFIÉ ce jalon)
      -> actualSales = min(totalDemand, effectiveCapacity)   -- AUCUNE seconde loterie
      -> transforme actualSales en revenue/variableCosts
```

Invariant fondamental (familles transactionnelles — service/hospitality/retail/agency) :
```
actualSales    = min(totalDemand, effectiveCapacity)
lostToCapacity = totalDemand - actualSales
actualSales + lostToCapacity = totalDemand   (à epsilon flottant près)
```
`effectiveCapacity` = la capacité déjà calculée par `businessResolution.ts`
(`capacityHours`, `coversCapacity`, `min(stockUnits, laborCapacityUnits)`,
`capacityMandates`) — strictement inchangée par ce jalon.

## §2. Service — nouvelle équation

Fichier : `src/engine/economic-models/service.ts`.

```ts
export function computeServiceMonth(
  state: ServiceEngineState,
  decisions: ServiceEngineDecisions,
  _ctx: EconomicEngineContext,
): ServiceMonthContribution {
  // ... validations inchangées ...
  const hoursSold = Math.min(decisions.targetHours, decisions.capacityHours);
  const utilizationRate = decisions.capacityHours > 0 ? hoursSold / decisions.capacityHours : 0;
  return {
    revenue: hoursSold * state.hourlyRate,
    variableCosts: hoursSold * state.costPerLaborHour,
    hoursSold,
    utilizationRate,
  };
}
```
Suppressions : `BASE_UTILIZATION`, `REPUTATION_UTILIZATION_BONUS`,
`UTILIZATION_NOISE_STD_DEV`, l'appel `ctx.rng.nextGaussian`. `ctx` renommé
`_ctx` (paramètre requis par l'interface `EconomicEngine`, mais plus
utilisé dans ce moteur précis — `noUnusedParameters` du tsconfig l'exige ;
la signature PUBLIQUE `EconomicEngine<...>.computeMonth(state, decisions, ctx)`
ne change pas, seul le nom local du paramètre change). `utilizationRate`
redéfini en métrique purement descriptive, ne pilote plus `hoursSold`.
`ServiceEngineState.reputationScore` reste dans l'interface (aucun
changement d'interface publique demandé) mais n'est plus lu par
`computeServiceMonth` — la réputation influence déjà `totalDemand` en amont
via `computeOfferDemand`/`computeSegmentFit` (trustFit) et
`computeVisibilityFactor`, jamais une seconde fois ici (§9 de l'énoncé).

## §8. Réputation — non-double-comptage explicite

La réputation influence déjà `totalDemand` (via `computeOfferDemand` :
`computeSegmentFit`'s `trustFit`, `computeVisibilityFactor`'s poids
réputation) et la réputation elle-même évolue selon la satisfaction des
clients servis (`computeReputationUpdate`, M11.2.3, inchangé). Après ce
jalon, elle n'entre plus JAMAIS dans la conversion demande captée → vente
des 4 moteurs économiques transactionnels. Test dédié (§11) : deux
résolutions avec `totalDemand`/capacité/prix/coûts identiques mais des
`reputationScore` différents doivent produire un `actualSales` strictement
identique.

## §9. RNG — retiré précisément où

Retiré des 4 fonctions `computeXMonth` (service/hospitality/retail/agency)

jalon. **Conservé** :
- `computeSubscriptionMonth` (`churnRate` — résiliation, phénomène

- Tout le reste du moteur (RNG du monde/marché/concurrence/événements,

## §10. Calibration — assumé, non compensé ce jalon

Retirer les anciens `BASE_UTILIZATION`/`BASE_FILL_RATE`/`BASE_CONVERSION_RATE`/
`BASE_WIN_RATE` (tous < 1, typiquement 0.2-0.5) va mécaniquement AUGMENTER
les ventes de toute entreprise dont la demande captée dépasse ou approche
sa capacité (cas déjà documenté comme fréquent pour Hospitality, cf le
rapport de playtest M11.2.3.1 — non corrigé ici, énoncé §18 explicite).
Aucune compensation dans `computeOfferDemand` ni dans les constantes de
marché (`src/scenarios/markets.ts`) : ce jalon ne fait QUE retirer la
seconde loterie commerciale, il ne recalibre pas l'équilibre économique
résultant. Les déséquilibres observés lors des tests/playtests sont
documentés dans le rapport final, pas corrigés.
