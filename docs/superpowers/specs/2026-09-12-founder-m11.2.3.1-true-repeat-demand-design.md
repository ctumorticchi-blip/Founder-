# FOUNDER — M11.2.3.1 « True Repeat Demand » — Spec

Base : commit `65c7a4a` (M11.2.3, déjà sur `main`).

## §0. Constat validé par l'inspection

Le diagnostic de la demande est confirmé par la lecture intégrale de
`src/engine/customer/retention.ts` et `src/engine/simulation/businessResolution.ts` :

Aujourd'hui, pour chaque offre lancée d'une famille transactionnelle
(service/hospitality/retail/agency), la séquence exacte est :

```
funnel = computeOfferDemand(...)               // demande d'ACQUISITION uniquement
contribution = computeXMonth(..., capacity, funnel.demand)  // -> sales (unique nombre)
resolveOfferSatisfaction(..., actualSales=contribution.sales, ...)
  -> updateSegmentMemory(prev, ..., actualVolumeThisMonth=segmentSales, ...)
       retainedVolumeThisMonth = min(actualVolumeThisMonth, priorBase * repeatRate)
       newVolumeThisMonth = actualVolumeThisMonth - retainedVolumeThisMonth
```

`retainedBaseVolume`/`repeatRate` ne participent à AUCUN moment au calcul de
`funnel.demand` ni de `contribution.sales`. Ils ne font que RECLASSER après
coup une partie d'un volume de ventes déjà entièrement déterminé par
`computeOfferDemand` (acquisition) + le moteur économique de capacité. Une
entreprise avec une base fidèle énorme mais un `funnel.demand` nul (aucune
visibilité/aucun marché) afficherait `retainedVolumeThisMonth = 0` — alors
qu'intuitivement ses habitués devraient continuer à vouloir revenir. Le
diagnostic de l'énoncé est donc exact : **STOP non déclenché**, on implémente.

Point technique additionnel découvert à l'inspection, qui contraint la
conception de l'allocation capacité (§4/§6 plus bas) : chaque moteur
économique de famille (`computeServiceMonth`, `computeHospitalityMonth`,
`RetailEngine.computeMonth`, `AgencyEngine.computeMonth`) applique DÉJÀ un
taux de conversion interne + bruit RNG entre `min(demande, capacité)` et la
vente réelle (`utilizationRate`/`conversionRate`, préexistant à M11.2,
inchangé). La vente réelle totale (`contribution.sales`) est donc UN SEUL
nombre, jamais nativement scindé nouveaux/récurrents par le moteur
économique lui-même — la ventilation nouveaux/récurrents doit se faire
PAR ALLOCATION PROPORTIONNELLE après coup, exactement comme le fait déjà
`resolveOfferSatisfaction` aujourd'hui pour ventiler `actualSales` par
segment (`segmentSales = actualSales * seg.demand/totalSegmentDemand`). On
réutilise ce même principe, imbriqué sur un niveau supplémentaire
(segment × flux nouveaux/récurrents), sans jamais dupliquer ni
resimuler le moteur économique de la famille (spec M11.2.3.1 §4/§18).

## §1. Principe

Nouvelle causalité, remplaçant l'actuelle « demande d'acquisition → capacité
→ ventes → reclassement » :

```
newDemand   = computeOfferDemand(...)               // INCHANGÉ, M11.2.2
repeatDemand = computeRepeatDemand(priorMemory)      // NOUVEAU
totalDemand  = newDemand + repeatDemand
capacity     = (inchangé par famille)
sales        = computeXMonth(..., capacity, totalDemand)   // moteur économique INCHANGÉ, juste sa cible change
newSales, repeatSales     = allocation proportionnelle de `sales` entre newDemand et repeatDemand
unservedNew, unservedRepeat = allocation proportionnelle de `lostToCapacity` (= max(0, totalDemand - capacity))
```

Trois mécanismes strictement distincts et non redondants :
- **Acquisition** — `computeOfferDemand` (M11.2.2, intouché) : marché → exposition → intérêt → `newDemand`.
- **Retention** — `computeRepeatDemand` (nouveau, M11.2.3.1) : base client existante × propension au retour → `repeatDemand`.
- **Word-of-mouth** — `computeWordOfMouth` (M11.2.3, intouché) : satisfaction + volume lissés → facteur d'appoint de VISIBILITÉ, qui influence `computeOfferDemand` (donc `newDemand`) via `organicWordOfMouth`. Il n'entre JAMAIS dans `computeRepeatDemand`.

Aucun double comptage : `repeatDemand` ne traverse jamais `computeOfferDemand` ; `organicWordOfMouth` ne traverse jamais `computeRepeatDemand`.

## §2. `computeRepeatDemand` — nouvelle fonction pure

Fichier : `src/engine/customer/retention.ts` (même module que `computeRepeatRate`/`updateSegmentMemory`, cohérent avec le découpage `engine/customer/*` = concerns rétention, `engine/market/demand.ts` = concerns acquisition).

Approche **B — base client × propension au retour**, validée par l'énoncé (pas de fréquence d'achat par métier — ce sera le Universal Business Builder, hors scope ici).

```ts
export function computeRepeatDemand(memory: SegmentCustomerMemory | null): number {
  if (memory === null) return 0;
  const propensity = computeRepeatRate(memory.smoothedSatisfactionScore) * (1 - memory.availabilityFrustration);
  return memory.retainedBaseVolume * propensity;
}
```

- `memory === null` (aucun premier contact) → `0` (test §15).
- Dépend au minimum de `retainedBaseVolume`, de la propension au retour dérivée de la satisfaction lissée (`computeRepeatRate`, déjà existant, RÉUTILISÉ tel quel), et de `availabilityFrustration` (nouveau, §5) — trois grandeurs déjà présentes/ajoutées à `SegmentCustomerMemory`, aucune nouvelle mémoire globale.
- Extensibilité Universal Business Builder : la fonction prend la mémoire ENTIÈRE en entrée (pas juste 2-3 scalaires épars) — un futur ajout de fréquence naturelle de consommation par métier pourra multiplier `propensity` par un facteur de fréquence sans changer la signature ni le point d'appel.
- Pure, déterministe, aucun accès à `computeOfferDemand` ni au marché.

## §3. Allocation capacité — proportionnelle pure, aucune priorité cachée

Décision produit validée (énoncé §6) : ni les nouveaux ni les habitués ne
sont prioritaires. Implémentation dans `businessResolution.ts`, PAR SEGMENT
(le funnel `bySegment` couvre déjà tous les segments, `computeOfferDemand`
inchangé) :

```
Pour chaque segment s de funnel.bySegment :
  newDemand_s    = s.demand                                    // déjà calculé, M11.2.2
  repeatDemand_s = computeRepeatDemand(priorMemoryOf(s))        // nouveau
  totalDemand_s  = newDemand_s + repeatDemand_s

totalDemand = Σ totalDemand_s   // -> targetX du moteur économique (remplace funnel.demand)
capacity    = (calcul de capacité de la famille, INCHANGÉ)
contribution = computeXMonth(..., capacity, totalDemand)   // moteur économique INCHANGÉ
lostToCapacity = max(0, totalDemand - capacity)             // remplace max(0, funnel.demand - capacity)

Pour chaque segment s :
  share_s        = totalDemand > 0 ? totalDemand_s / totalDemand : 0
  segmentSales_s = contribution.sales * share_s
  segmentLost_s  = lostToCapacity * share_s
  newShare_s     = totalDemand_s > 0 ? newDemand_s / totalDemand_s : 0
  newSales_s        = segmentSales_s * newShare_s
  repeatSales_s      = segmentSales_s * (1 - newShare_s)
  unservedNew_s       = segmentLost_s * newShare_s
  unservedRepeat_s    = segmentLost_s * (1 - newShare_s)
```

Propriétés garanties par construction (tests §7 de ce document) :
- `Σ newSales_s + Σ repeatSales_s = contribution.sales` (à l'arrondi flottant près).
- `Σ unservedNew_s + Σ unservedRepeat_s = lostToCapacity`.
- Aucune priorité : le ratio new/repeat servi dans un segment est identique au ratio new/repeat demandé dans ce segment (`newSales_s/repeatSales_s = newDemand_s/repeatDemand_s` quand `segmentSales_s>0`).

`offer.lastDemand.demand` (persisté, affiché dans la carte "Ce mois-ci")
devient `totalDemand` — cohérence interne obligatoire avec
`capacity`/`sales`/`lostToCapacity` du même objet (un joueur ne doit jamais
voir "Demande: 40 / Capacité: 100" ET "Ventes perdues: 12" simultanément,
incohérence qui existerait si `.demand` restait new-only pendant que
`lostToCapacity` inclut le repeat). `computeOfferDemand`/`DemandFunnelResult`
restent **strictement inchangés** (aucune modification de
`src/types/demand.ts` ni `src/engine/market/demand.ts`) : l'override de
`.demand` se fait uniquement au point d'assemblage dans
`businessResolution.ts`, par un simple remplacement de propriété
(`{...funnel, demand: totalDemand, capacity, sales, lostToCapacity}`),
exactement le même genre de spread déjà utilisé aujourd'hui.
`demandSignal`/`availableMarket`/`bySegment` restent des grandeurs
d'ACQUISITION pures (calculées par `computeOfferDemand`, jamais touchées) —
ce sont des signaux de marché, pas des signaux de capacité.

## §4. Ventes perdues des clients récurrents ≠ mauvaise expérience

`unservedRepeat_s` (agrégé sur les segments d'une offre) ne modifie JAMAIS
`smoothedSatisfactionScore` ni le diagnostic de satisfaction — la
satisfaction reste calculée UNIQUEMENT sur `newSales_s + repeatSales_s`
(les clients réellement servis), exactement comme aujourd'hui (§10 de
l'énoncé, aucun changement de sens).

`unservedRepeat_s` alimente un mécanisme séparé et nouveau :
`availabilityFrustration` (par segment, dans `SegmentCustomerMemory`).

## §5. Frustration de disponibilité — nouveau champ, lissé, à inertie

```ts
availabilityFrustration: number   // 0-1, EWMA, persisté par segment
```

Mise à jour dans `updateSegmentMemory` :

```ts
const refusalRate =
  repeatDemandThisMonth > 0 ? clamp(unservedRepeatDemandThisMonth / repeatDemandThisMonth, 0, 1) : null;
const availabilityFrustration =
  refusalRate === null
    ? (previous?.availabilityFrustration ?? 0)               // aucune demande de retour ce mois -> aucun signal, on ne bouge rien
    : (previous?.availabilityFrustration ?? 0) * (1 - FRUSTRATION_EWMA_ALPHA) + refusalRate * FRUSTRATION_EWMA_ALPHA;
```

`FRUSTRATION_EWMA_ALPHA` choisi petit (même ordre que `SATISFACTION_EWMA_ALPHA=0.35`)
pour qu'un refus ponctuel (`refusalRate` élevé un seul mois) ait un effet
FAIBLE sur la moyenne lissée (§17 test "refus ponctuel → faible
conséquence"), mais que des refus RÉPÉTÉS l'accumulent progressivement vers
1 (§17 test "refus répétés → frustration augmente"). La même formule EWMA
porte NATIVEMENT la redescente progressive quand la capacité redevient
suffisante (`refusalRate` retombe à 0, la moyenne lissée redescend
progressivement vers 0 — jamais un reset instantané), satisfaisant §17
"la disponibilité doit s'améliorer... progressivement, pas instantanément"
sans mécanisme dédié supplémentaire.

`availabilityFrustration` réduit `computeRepeatDemand`'s `propensity`
(§2) — donc une frustration élevée soutenue fait mécaniquement baisser
`repeatDemand` dans les mois suivants, qui fait baisser `actualVolumeThisMonth`
servi, qui fait EWMA-décroître `retainedBaseVolume` (mécanisme déjà
existant, inchangé) : l'érosion de la base est donc une CONSÉQUENCE
naturelle de la baisse de propension, sans champ supplémentaire dédié à
l'érosion (principe §8 de l'énoncé : « évite de stocker des valeurs
pouvant être dérivées proprement »).

## §6. `SegmentCustomerMemory` — extension minimale

Trois champs ajoutés (noms choisis après inspection du type réel dans
`src/types/satisfaction.ts`) :

```ts
export interface SegmentCustomerMemory {
  // ... champs M11.2.3 inchangés ...
  /** Demande récurrente calculée ce mois-ci par `computeRepeatDemand`, AVANT allocation de capacité (spec M11.2.3.1 §2). */
  readonly repeatDemandThisMonth: number;
  /** Part de `repeatDemandThisMonth` non servie faute de capacité (spec §3-4) — jamais assimilée à une mauvaise expérience. */
  readonly unservedRepeatDemandThisMonth: number;
  /** Frustration de disponibilité lissée (EWMA), 0-1 — distincte de la satisfaction (spec §5). */
  readonly availabilityFrustration: number;

```

Portée inchangée : entreprise × offre × segment (`offer.customerMemory: readonly SegmentCustomerMemory[]`).

## §7. `updateSegmentMemory` — nouvelle signature, flux réels

Signature actuelle (M11.2.3, à remplacer — changement justifié, §9 de
l'énoncé : la fonction ne doit plus reclasser après coup) :

```ts
updateSegmentMemory(previous, segmentId, segmentLabel, actualVolumeThisMonth, satisfactionThisMonth, diagnosisThisMonth)
```

Nouvelle signature (objet de contexte — 8 grandeurs, trop pour du
positionnel clair) :

```ts
export interface SegmentMemoryUpdateInput {
  readonly segmentId: string;
  readonly segmentLabel: string;
  /** Nouveaux clients EFFECTIVEMENT SERVIS ce mois-ci (flux réel, plus une reclassification, spec §9). */
  readonly newVolumeThisMonth: number;
  /** Clients récurrents EFFECTIVEMENT SERVIS ce mois-ci (flux réel, spec §9). */
  readonly retainedVolumeThisMonth: number;
  /** Demande récurrente calculée ce mois-ci (spec §5), avant capacité. `0` si aucune mémoire préalable. */
  readonly repeatDemandThisMonth: number;
  /** Part de `repeatDemandThisMonth` refusée faute de capacité (spec §4). */
  readonly unservedRepeatDemandThisMonth: number;
  /** `null` si aucune vente servie ce mois-ci pour ce segment (aucune mesure de satisfaction possible). */
  readonly satisfactionThisMonth: number | null;
  readonly diagnosisThisMonth: SatisfactionDiagnosis | null;
}

export function updateSegmentMemory(previous: SegmentCustomerMemory | null, input: SegmentMemoryUpdateInput): SegmentCustomerMemory
```

Logique interne :
- `retainedBaseVolume` : EWMA inchangée dans sa FORME, mais désormais vers
  `newVolumeThisMonth + retainedVolumeThisMonth` (flux réel total servi,
  au lieu de l'ancien `actualVolumeThisMonth` déjà correct numériquement —
  aucune régression de calcul, seule la provenance du nombre change).
- `cumulativeAcquiredVolume += newVolumeThisMonth` — désormais un VRAI flux
  de nouveaux clients servis, jamais un reste de soustraction (§9 : plus
  aucun risque de double comptage par construction).
- `smoothedSatisfactionScore`/`consecutiveGoodMonths`/`consecutiveBadMonths`/
  `lastSatisfactionScore`/`lastDiagnosis` : logique inchangée.
- `monthsSinceFirstSale` : condition `actualVolumeThisMonth > 0` devient
  `newVolumeThisMonth + retainedVolumeThisMonth > 0`.
- `availabilityFrustration` : nouveau, §5.
- `repeatDemandThisMonth`/`unservedRepeatDemandThisMonth` : persistés tels
  quels (informatifs + entrée du calcul de frustration du mois prochain).

## §8. `businessResolution.ts` — remplacement de `resolveOfferSatisfaction`

Renommée `resolveOfferOutcome` (elle ne produit plus seulement de la
satisfaction mais aussi l'allocation new/repeat — le nom doit refléter ce
qu'elle fait réellement). Nouvelle signature :

```ts
function resolveOfferOutcome(
  offer: Offer,
  segments: readonly CustomerSegment[],
  funnel: Omit<DemandFunnelResult, "capacity" | "sales" | "lostToCapacity">,
  deliveredExperience: number,
  operationalPenalty: number,
  totalSales: number,        // contribution.sales — un seul nombre, moteur économique inchangé
  totalLostToCapacity: number,  // lostToCapacity au niveau de l'offre
  reputationScore: number,
): {
  readonly updatedMemory: readonly SegmentCustomerMemory[];
  readonly volumeForReputation: number;      // = totalSales, inchangé
  readonly satisfactionForReputation: number; // inchangé, calculé sur les clients servis
}
```

À l'intérieur, pour chaque segment de `funnel.bySegment` : calcule
`repeatDemand_s` via `computeRepeatDemand(priorMemory)`, applique
l'allocation proportionnelle du §3, calcule la satisfaction sur
`newSales_s + repeatSales_s` (inchangé dans sa formule), appelle le nouveau
`updateSegmentMemory`.

**Subscription (§12 de l'énoncé)** : n'utilise PAS `computeRepeatDemand`.
Son bloc dans `resolveBusinessMonth` reste inchangé dans sa logique
économique (`activeSubscribers + acquisition - churn`, `effectiveChurnRate`
piloté par la satisfaction déjà en place). Le SEUL point de contact avec
`resolveOfferOutcome` : appelé avec `totalSales = funnel.demand` (comme
aujourd'hui) et implicitement `repeatDemand_s = 0` pour tous les segments
(pas de calcul de repeat demand pour cette famille) — `newVolumeThisMonth`
absorbe donc 100% du flux, `retainedVolumeThisMonth`/
`unservedRepeatDemandThisMonth` restent à `0`. C'est un choix EXPLICITE et
documenté, pas un oubli : la vraie mécanique de rétention de Subscription
est `activeSubscribers`, pas la mémoire par segment (qui ne sert ici qu'au
bouche-à-oreille/diagnostic/satisfaction, déjà le cas en M11.2.3).

**Agency (§13 de l'énoncé)** : traité EXACTEMENT comme service/hospitality/
retail (bloc transactionnel générique) — `repeatDemand` y représente le
retour statistique agrégé d'anciens clients, pas des contrats nommés
(Strategic Accounts reste hors scope, M11.2.4).

## §11. Invariants transverses (rappel, non renégociables)

- Aucun `Math.random`, aucune resimulation du moteur de demande/économique.
- `computeOfferDemand` et son type `DemandFunnelResult` restent
  inchangés — seule leur consommation dans `businessResolution.ts` évolue.
- `computeWordOfMouth` reste un facteur de VISIBILITÉ pur, jamais consommé
  par `computeRepeatDemand`.
- La satisfaction reste calculée uniquement sur les clients servis.
- La réputation reste pilotée par cette même satisfaction pondérée par le
  volume réel total servi (`totalSales`) — aucun changement de formule,
  seul le volume qui l'alimente peut désormais inclure des ventes
  récurrentes réelles (déjà le cas indirectement en M11.2.3 via
  `actualSales`, donc non-régressif).
- Cinq familles, mécaniques pas nécessairement identiques (Subscription
  différente, assumé et documenté).
