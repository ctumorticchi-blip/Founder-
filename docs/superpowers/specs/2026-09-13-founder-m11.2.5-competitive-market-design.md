Décision produit verrouillée (issue GitHub #1, PRODUCT DECISION REQUIRED
résolue) : **Option C**. M11.2.5 livre une couche de concurrents
**identifiés et nommés**, décomposition purement additive de la

  sont hors P0". M11.2.5 active le tier `"identified"` ; `"major"` reste

- `src/engine/intelligence/intelligence.ts` : `estimate(trueValue, skill,

  **ne sont appelés nulle part côté web** (`git grep` confirmé) : la
  projection d'information imparfaite du marché est un morceau de moteur
  jamais branché à l'UI. Hors scope de corriger ça pour `Market` lui-même
  ici (appartient à M11.2.6 "Market Intelligence & UX" par son nom même),
  mais le PATRON (`estimate` + bucket qualitatif, jamais un score brut) est
  directement réutilisé pour projeter les concurrents identifiés.
- `src/engine/business/strategicAccountIdentity.ts` : patron déjà éprouvé
  de génération déterministe de noms d'entreprises fictives (préfixe +
  racine + suffixe, listes plates, `rng.pick`) — réutilisé tel quel pour
  nommer les concurrents (pas de nouveau générateur de noms de personnes,
  un concurrent est une entreprise, pas un contact).
- Bucket qualitatif : patron `bucketVisibility`/`bucketPriceSignal`/
  `bucketDemandSignal` (`market/demand.ts`) — jamais un nombre brut affiché
  au joueur, toujours 3 paliers qualitatifs. Réutilisé à l'identique pour
  "part de marché estimée" et "positionnement estimé" d'un concurrent.

## §1. Le point critique — décomposition sans double état à synchroniser

Un concurrent identifié ne stocke **pas** sa part de marché : il stocke
seulement un `strength` relatif (poids). La part de marché d'un concurrent
est **toujours** une fonction pure dérivée à la lecture :

```
competitorMarketShare(competitor, allCompetitorsOfSameMarket, aggregate)
  = (competitor.strength / sum(strengths du marché)) * aggregate.totalCapturedRevenueShare
```

Conséquence directe : la somme des parts de marché affichées des
concurrents identifiés d'un marché est **structurellement toujours égale**
à `aggregate.totalCapturedRevenueShare` (identité mathématique, pas un
invariant à re-vérifier à chaque évolution). Quand l'agrégat dérive
(`advanceAggregateCompetition`), les parts individuelles suivent
automatiquement, sans code de synchronisation dédié, sans jamais pouvoir
diverger. C'est la façon dont ce système reste **additif et sans risque**
pour l'agrégat existant : `AggregateCompetition` continue d'être calculé
exactement comme avant (aucune ligne touchée), les concurrents identifiés
ne font qu'en offrir une lecture décomposée.

`qualityLevel` (0-1), lui, est stocké directement par concurrent (pas
dérivé) : il n'a pas de contrainte de somme à préserver, juste une dérive
lente centrée sur `aggregate.averageQuality` (même patron que le drift de
l'agrégat lui-même).

## §4. Intégration `simulateMonth.ts` — backfill des sauvegardes existantes SANS fabriquer d'historique

`createInitialGameState` peuple `competitors` pour chaque marché dès la
création d'une NOUVELLE partie (même point que `competitionsById`,
`game.ts:34`).

Pour les sauvegardes EXISTANTES (créées avant ce milestone), la migration
web (`storage.ts`) ne fabrique **aucun concurrent fictif** — conformément
à la règle CLAUDE.md ("jamais une valeur inventée pour compenser une
donnée manquante") : `competitors: save.gameState.competitors ?? {}`,
neutre. Dans `simulateMonth.ts`, au même point que la boucle
`advanceAggregateCompetition` (`simulateMonth.ts:132`), si
`competitors[marketId]` est absent/vide pour un marché, on appelle
`createIdentifiedCompetitors` (première apparition RÉELLE dans CETTE
partie, pas une reconstitution de passé) au lieu de
`advanceIdentifiedCompetitors` ce mois-ci. Une seule fonction de création,
réutilisée à l'identique pour une partie neuve et pour le rattrapage d'une
sauvegarde ancienne — pas de deuxième chemin de code à maintenir.

## §5. Information imparfaite — jamais un score brut affiché

Nouvelle fonction miroir de `bucketPriceSignal`/`bucketVisibility` :

```ts
// src/engine/intelligence/intelligence.ts (ajout, aucune fonction existante modifiée)
export type CompetitivePositionLevel = "economy" | "standard" | "premium";
export type MarketShareLevel = "low" | "moderate" | "high";

export function projectCompetitorView(
  competitor: Competitor,
  marketShare: number,       // déjà calculée par computeCompetitorMarketShare
  skillAverage0To100: number,
  rng: Rng,
): { readonly name: string; readonly positionLevel: CompetitivePositionLevel; readonly shareLevel: MarketShareLevel }
```

`qualityLevel` et `marketShare` passent par `estimate()` (bruit, jamais 0)
avant d'être bucketés — un joueur à faible compétence finance/stratégie
voit une estimation plus grossière, cohérent avec `projectMarketView`
existant. Le NOM du concurrent n'est jamais bruité (une identité n'est pas
une grandeur économique).

## §6. UX — écran minimal, pas la consolidation complète (hors scope M11.2.6)

Un nouvel écran/section "Concurrents identifiés" (accessible depuis
l'écran Entreprise existant, par marché) liste, par concurrent : nom +
positionnement estimé (libellé qualitatif) + part de marché estimée
(libellé qualitatif). Aucun id technique, aucun score brut, mobile-first.
**Volontairement minimal** : pas de tri/filtre avancé, pas de tendance
historique affichée, pas de fusion avec l'écran marché existant — cette
consolidation UX appartient explicitement à M11.2.6 ("Market Intelligence
& UX"), pas ici. Le critère de complétude de M11.2.5 est : le joueur peut
voir, pour un marché où il opère, qui sont ses concurrents identifiés et
une estimation qualitative de leur position — rien de plus.
