# FOUNDER — M11.2.2 « Customer & Demand Engine » — Amendement de spec

Amendement à `docs/superpowers/specs/2026-09-10-founder-m11.2-design.md` §4
(qui ne donnait qu'une esquisse d'architecture). Base : `main` à
`0246a1a24d1d26e8a7905b82c54ead4bd5bd4c65` (M11.2.1 validée, moteur à 328
tests, web à 72 tests).

## 0. Constat central (ce que M11.2.2 doit réellement changer)

Aujourd'hui, `businessResolution.ts` calcule le revenu ainsi, pour les 5
familles :

```ts
targetHours: action.decisions.targetHours * demandShare   // service
expectedDemandCovers: action.decisions.expectedDemandCovers * demandShare // hospitality
newSubscribers: action.decisions.newSubscribers * demandShare             // subscription
expectedFootTraffic: action.decisions.expectedFootTraffic * demandShare   // retail
targetMandates: action.decisions.targetMandates * demandShare             // agency
```

`decisions.targetHours`/etc. sont eux-mêmes calculés côté web
(`commercialTranslation.ts::deriveTargetValue`) par un simple produit
`prospectionHours × coefficient_par_famille` — **aucun segment, aucune
adéquation offre/marché, aucun entonnoir réel**. C'est exactement la
mécanique que M11.2.2 doit faire disparaître : ces cinq champs sont
**supprimés du type** `BusinessFamilyDecisions` (pas seulement ignorés),
et remplacés par une valeur calculée par le nouveau Customer & Demand
Engine à partir de l'offre active, des segments du marché et de la
demande captée — vérifiable par `git grep -n "targetHours\|expectedDemandCovers\|expectedFootTraffic\|targetMandates\|newSubscribers" src/engine/simulation src/types/simulation web/src/state` qui ne doit plus rien trouver côté décisions du joueur (seules les
signatures internes `ServiceEngineDecisions`/etc. de
`economic-models/*.ts`, **inchangées**, conservent ces noms de champs —
c'est la forme d'entrée déjà existante de fonctions qui restent
elles-mêmes intactes).

## 1. Principe

> marché → segments → exposition → adéquation offre/segment → intention
> d'achat → demande → capacité → ventes

Le moteur économique historique (`economic-models/*.ts`, la conversion
capacité+cible → revenu avec taux de remplissage/conversion/transformation
et bruit RNG) **reste inchangé et continue d'exister** : il représente
« combien de la demande qui se présente est effectivement exécutée avec
succès », une couche d'exécution distincte de « combien de demande se
présente ». Le Customer & Demand Engine (nouveau) calcule cette seconde
grandeur et **remplace la source de la « cible »** envoyée à la première —
exactement le motif déjà utilisé trois fois (infrastructure, immobilier,
temps de prospection) : nouvelle couche qui *alimente* un calcul
historique inchangé, jamais une duplication.

## 2. Segments clients (moteur, nouveau, données statiques)

`src/types/customerSegment.ts` :

```ts
export interface CustomerSegment {
  readonly id: string;
  readonly label: string;                    // vocabulaire métier, ex. "Entreprises exigeantes"
  readonly relativeSize: number;             // part du marché de la famille, 0-1 (les segments d'une famille somment à 1)
  readonly referencePrice: number;           // prix "normal" perçu par ce segment, dans l'unité native de la famille
  readonly preferredPositioning: OfferPositioning;
  readonly priceSensitivity: number;         // 0-1 : sévérité de la pénalité si le prix dépasse referencePrice
  readonly qualityExpectation: number;       // 0-100 : qualité en-deçà de laquelle l'offre déçoit
  readonly trustImportance: number;          // 0-1 : poids de la réputation dans l'adéquation
  readonly structuralTrend: number;          // dérive linéaire de relativeSize par mois d'ancienneté de l'offre (petit, signé)
  readonly seasonality: readonly number[];   // 12 multiplicateurs (index 0 = janvier), centrés sur 1
}
```

`src/engine/market/segments.ts` : `getMarketSegments(family): readonly
CustomerSegment[]` — catalogue statique, **4 segments par famille**
(dans la fourchette 3-5 demandée), `relativeSize` sommant à 1 par famille,
`referencePrice` calibré sur les prix déjà recommandés par
`opportunities.ts` (service ~45, hospitality ~26, retail ~15, agency
~6000, subscription ~29), avec une vraie diversité economy/standard/
premium et des saisonnalités différentes (`FLAT`/`SUMMER_PEAK`/
`WINTER_PEAK`/`YEAR_END_PEAK`, 4 courbes canoniques réutilisées). Donnée
pure, déterministe par construction (pas de RNG) — un catalogue statique
au même titre que `INFRASTRUCTURE_OPTIONS` ou `offerModels.ts`, **pas un
état persisté** (aucune migration nécessaire pour les segments eux-mêmes :
`getMarketSegments("service")` renvoie toujours le même résultat).

## 3. Product–Market Fit (moteur, pur, composantes conservées)

`src/types/demand.ts` :

```ts
export interface FitBreakdown {
  readonly priceFit: number;        // 0-1
  readonly qualityFit: number;      // 0-1
  readonly positioningFit: number;  // 0-1
  readonly trustFit: number;        // 0-1
  readonly overallFit: number;      // 0-1, combinaison pondérée par les poids DU SEGMENT
}
```

`src/engine/market/demand.ts::computeSegmentFit(offer, segment,
reputationScore, isPrimaryTarget): FitBreakdown` :
- `priceFit` : pénalise `offer.price` au-dessus de `segment.referencePrice`,
  proportionnellement à `segment.priceSensitivity` ; un prix inférieur
  n'est jamais pénalisé (léger avantage plafonné).
- `qualityFit` : `clamp(offer.qualityLevel / segment.qualityExpectation, 0, 1)`.
- `positioningFit` : distance catégorielle entre `offer.positioning` et
  `segment.preferredPositioning` sur l'échelle economy/standard/premium
  (0 d'écart → 1 ; 1 → 0,6 ; 2 → 0,25).
- `trustFit` : `reputationScore` (0-1, déjà porté par `familyState`).
- `overallFit` : moyenne pondérée, poids = `{price: priceSensitivity,
  quality: 1, positioning: 0.6, trust: trustImportance}`, **+ petit bonus
  additif si `segment.id === offer.targetSegment`** (avantage
  d'adéquation raisonnable, spec §2 : jamais une exclusivité — les autres
  segments restent pleinement évalués et peuvent dominer la demande).

Aucune composante n'est écrasée par un score unique avant la fin : le
`FitBreakdown` complet est conservé dans le résultat persisté
(`Offer.lastDemand`, §5) pour l'explicabilité (§7).

## 4. Marché → disponibilité par segment (réutilise l'existant)

`market.sizeMonthlyRevenuePotential` porte déjà, sans changement, la
tendance structurelle du marché (`growthRateMonthly`) et la conjoncture du
World Engine (`macro.gdpGrowthRateAnnual × market.cyclicality`), appliquées
chaque mois par `advanceMarket` (**inchangé**). M11.2.2 ajoute uniquement
deux facteurs **au niveau segment**, tous deux déterministes :

```
monthsActive = monthsBetween(offer.createdAt, date)   // ancienneté de l'offre, pas une date calendaire absolue (évite toute dérive liée à l'année réelle de la partie)
effectiveRelativeSize = clamp(segment.relativeSize * (1 + segment.structuralTrend * monthsActive), 0, 1)
seasonalMultiplier = segment.seasonality[date.month - 1]
segmentRevenuePotential = market.sizeMonthlyRevenuePotential * effectiveRelativeSize * seasonalMultiplier
availableMarketUnits = segmentRevenuePotential / segment.referencePrice
```

Dérive **linéaire** (pas exponentielle) sur `monthsActive`, volontairement :
une composition exponentielle sur un index de mois absolu (`toMonthIndex`,
qui dépend de l'année calendaire réelle de la partie) exploserait ou
s'annulerait selon l'année de lancement de la partie — non déterministe
au sens produit. La dérive relative à l'ancienneté de l'offre reste bornée
et testable quel que soit le moment réel où la partie est jouée.

## 5. Entonnoir de demande (moteur, pur)

```ts
export interface DemandFunnelResult {
  readonly availableMarket: number;
  readonly reached: number;
  readonly interested: number;
  readonly demand: number;              // unité native de la famille (heures, couverts, unités, mandats, abonnés)
  readonly capacity: number;            // Infinity pour subscription (spec §8.3)
  readonly sales: number;
  readonly lostToCapacity: number;
  readonly topSegmentId: string;
  readonly topSegmentLabel: string;
  readonly fit: FitBreakdown;           // moyenne pondérée par contribution à la demande, tous segments
  readonly visibilityLevel: "low" | "medium" | "high";
  readonly priceSignal: "low" | "fair" | "high";
  readonly demandSignal: "weak" | "moderate" | "strong";
}
```

`computeOfferDemand(offer, market, segments, params: {demandShare,
reputationScore, prospectionHours, date}): Omit<DemandFunnelResult,
"capacity"|"sales"|"lostToCapacity">` — pure, déterministe (aucun RNG) :
1. Pour **chaque** segment (jamais seulement `offer.targetSegment`) :
   `availableMarketUnits` (§4), `fit` (§3), `reached = availableMarketUnits
   × exposureRate` (§6), `interested = reached × fit.overallFit ×
   MAX_INTEREST_CONVERSION`, `segmentDemand = interested ×
   DEMAND_UNIT_ADAPTER[family] × demandShare` (`demandShare` = part de
   marché non captée par la concurrence de fond, **valeur déjà calculée**
   par `availableDemandShare`, M4, inchangée — la concurrence réduit la
   demande atteignable, elle n'est pas dupliquée).
2. `demand`/`reached`/`interested`/`availableMarket` = sommes sur tous les
   segments. `topSegmentId`/`topSegmentLabel` = segment à la plus forte
   `segmentDemand` (peut différer de `offer.targetSegment`, spec §2).
   `fit` du résultat = moyenne des `FitBreakdown` par segment, pondérée par
   `segmentDemand`.
3. `visibilityLevel`/`priceSignal`/`demandSignal` : bucketage déterministe
   (§7) à partir de `exposureRate`/`fit.priceFit`/`fit.overallFit` —
   jamais la valeur brute.

`capacity`/`sales`/`lostToCapacity` sont calculés dans
`businessResolution.ts` (§6), pas dans `demand.ts`, car ils dépendent de
la capacité opérationnelle (déjà calculée par famille) et, pour plusieurs
offres, de l'ordre d'allocation (§8.4) — `demand.ts` ignore délibérément
la capacité pour rester une fonction de « marché », pas de « production ».

### 5.1 Acquisition organique (spec §7, transitoire)

`exposureRate = clamp(BASE_EXPOSURE_RATE + min(prospectionHours /
PROSPECTION_REFERENCE_HOURS, 1) × PROSPECTION_EXPOSURE_WEIGHT +
reputationScore × REPUTATION_EXPOSURE_WEIGHT, 0, MAX_EXPOSURE_RATE)`.
Trois leviers déjà disponibles dans l'architecture (prospection fondateur,
réputation) ; l'infrastructure/emplacement n'apporte aujourd'hui aucun
signal exploitable proprement (pas de notion de zone de chalandise) — non
ajouté, documenté comme extension possible pour M11.3 sans changer la
signature de `computeOfferDemand` (un paramètre optionnel s'ajouterait).
Aucun canal payant (pub, SEO, CRM) — strictement hors scope, remplacé
proprement par M11.3.

## 6. Intégration dans `resolveBusinessMonth` (moteur, changement substantiel assumé)

`resolveBusinessMonth` gagne un 7ᵉ paramètre `market: Market` (le marché
de l'entreprise, déjà avancé par `advanceMarket` avant l'appel dans
`simulateMonth.ts` — aucun nouveau calcul de marché, juste un paramètre
supplémentaire transmis). Pour chaque famille, le bloc `switch` est
réécrit ainsi (illustré sur `service`, identique dans l'esprit pour les 4
autres) :

```ts
const launchedOffers = offersAfterActions.filter(o => o.status === "launched");
let remainingCapacityHours = action.founderHoursAllocated + computeWorkforceCapacityHours(...); // inchangé
let totalRevenue = 0, totalVariableCosts = 0, totalUnitsForReputation = 0;
const segments = getMarketSegments(market.family);
const demandById = new Map<string, DemandFunnelResult>();
for (const offer of launchedOffers) {
  const funnel = computeOfferDemand(offer, market, segments, { demandShare, reputationScore: state.reputationScore, prospectionHours: action.founderProspectionHoursAllocated, date });
  const capacityForOffer = remainingCapacityHours;
  const contribution = computeServiceMonth(               // INCHANGÉ
    { hourlyRate: offer.price, costPerLaborHour: state.costPerLaborHour, reputationScore: state.reputationScore },
    { capacityHours: capacityForOffer, targetHours: funnel.demand },  // <-- seule la source de "targetHours" change
    { rng: rng.fork(`business:${owned.id}:service:${offer.id}`) },
  );
  totalRevenue += contribution.revenue;
  totalVariableCosts += contribution.variableCosts;
  totalUnitsForReputation += contribution.hoursSold;
  remainingCapacityHours = Math.max(0, remainingCapacityHours - contribution.hoursSold);
  demandById.set(offer.id, { ...funnel, capacity: capacityForOffer, sales: contribution.hoursSold, lostToCapacity: Math.max(0, funnel.demand - capacityForOffer) });
}
revenue = totalRevenue; variableCosts = totalVariableCosts;
familyState = launchedOffers.length > 0
  ? { ...state, reputationScore: clamp(state.reputationScore + totalUnitsForReputation * 0.0005, 0, 1) }
  : state;
```

`computeServiceMonth` (et les 4 autres fonctions économiques) ne changent
**pas une ligne** : seule la provenance de leur argument « cible » change
(du produit `decisions.target × demandShare` vers `funnel.demand`, déjà
multiplié par `demandShare` en amont dans `demand.ts` §5). C'est la preuve
vérifiable que le CA est désormais la conséquence de la demande captée et
de la capacité : `git grep -n "decisions\.\(targetHours\|expectedDemandCovers\|expectedFootTraffic\|targetMandates\|newSubscribers\)" src/` ne doit plus rien trouver — ces champs sont supprimés de
`BusinessFamilyDecisions` (§9), pas seulement inutilisés.

Sans offre lancée (`launchedOffers.length === 0`) : `revenue = 0`,
`variableCosts = 0`, réputation inchangée — comportement déjà établi par
M11.2.1, préservé.

### 6.1 Plusieurs offres (spec §9) : capacité partagée, séquentielle

La boucle ci-dessus s'applique **littéralement à plusieurs offres
lancées** : chaque offre calcule sa propre demande contre tous les
segments, puis consomme la capacité **restante** (ordre = ordre du
tableau `offers`, jamais réordonné, donc déterministe) — pas de nouvelle
mécanique de portefeuille, juste la réutilisation de la boucle existante.
`Offer.lastDemand` (§5) est donc **attribuable par offre**, résolvant
explicitement la limite M11.2.1 (« une seule offre économiquement
active »).

### 6.2 Correction Agency/Subscription (spec §8, dette M11.2.1 §3.6)

- **Agency** : `averageMonthlyFeePerMandate` transmis à `AgencyEngine.computeMonth`
  devient `offer.price` (au lieu de `state.averageMonthlyFeePerMandate`,
  figé à la création) — même boucle séquentielle que `service`, capacité
  = `capacityMandates` (inchangé). Sans offre lancée, `state.averageMonthlyFeePerMandate`
  ne sert plus jamais (cohérent : sans offre, pas de vente).
- **Subscription** : `computeSubscriptionMonth` n'a pas de plafond de
  capacité dans le moteur actuel (`newSubscribers` est toujours
  intégralement accepté — vérifié en lisant `subscription.ts` : aucune
  troncature) ; le funnel reflète honnêtement cette absence de contrainte
  (`capacity: Infinity`, `lostToCapacity: 0`) plutôt que d'inventer un
  plafond qui n'existe pas dans le moteur — limite documentée (§10),
  cohérente avec le modèle de dotation en personnel existant
  (`understaffingPenalty`, qui pénalise le *churn*, pas l'admission de
  nouveaux abonnés). `arpu` transmis devient `launchedOffers[0]?.price ??
  state.arpu` (le premier lancé par ordre de création fixe le tarif —
  seule grandeur que le modèle mono-tarif actuel peut représenter sans
  reconstruire une facturation par cohorte, hors scope) ; la demande de
  chaque offre lancée est sommée dans `newSubscribers` (chacune reste
  individuellement attribuable dans `lastDemand`, `sales = demand` faute
  de troncature à répartir).

## 7. Information imparfaite (spec §5, minimal)

Le moteur calcule des nombres exacts (`reached: 170`, etc. — des comptages,
pas des probabilités, donc affichables tels quels par cohérence avec
l'entonnoir demandé §6/§10). Ce qui ne doit **jamais** fuiter : les
coefficients de `CustomerSegment` (`priceSensitivity`, `qualityExpectation`,
`referencePrice`, `trustImportance`, `structuralTrend`) et le
`FitBreakdown` numérique brut. `DemandFunnelResult` expose donc, en plus
des comptages, trois signaux **déjà bucketés par le moteur** :
`visibilityLevel`/`priceSignal`/`demandSignal` (3 valeurs textuelles
chacun) — le web ne fait qu'afficher ces chaînes telles quelles, sans
recalcul ni interprétation (spec §11, explicabilité). Ce n'est pas
l'intelligence de marché complète (M11.2.6, non construite) — juste assez
pour qu'aucune vérité interne exacte ne soit montrée en M11.2.2.

## 8. Compatibilité 5 familles (spec §8)

Un seul module `demand.ts`/`segments.ts` pour les 5 familles ; les seules
variations par famille sont des **données** (`DEMAND_UNIT_ADAPTER`,
`referencePrice` des segments), jamais du code dupliqué. L'intégration
dans `resolveBusinessMonth` répète le même schéma de boucle dans chacun
des 5 blocs `switch` (déjà des blocs séparés avant M11.2.2, pour les
raisons de typage par famille déjà en place depuis le P0) — c'est une
répétition de **schéma**, pas de logique de demande (celle-ci vit
entièrement dans `demand.ts`, appelée identiquement).

## 9. Type `BusinessFamilyDecisions` (moteur, simplifié)

```ts
export type BusinessFamilyDecisions =
  | { readonly family: "service"; readonly price: number }
  | { readonly family: "hospitality"; readonly averageTicketPrice: number }
  | { readonly family: "subscription" }
  | { readonly family: "retail"; readonly unitPrice: number; readonly stockUnits: number }
  | { readonly family: "agency" };
```

`targetHours`/`expectedDemandCovers`/`newSubscribers`/`expectedFootTraffic`/
`targetMandates` supprimés — ils ne sont plus lus nulle part dans
`resolveBusinessMonth`. `retail.stockUnits` reste (contrainte d'inventaire
réelle, indépendante de la demande, déjà utilisée comme plafond de
capacité). Web (`commercialTranslation.ts`) : `deriveDecisions` perd son
paramètre `prospectionHours` et toute la table `PROSPECTION_HOURS_MULTIPLIER`/

plus que construire `{family, price}`/`{family, averageTicketPrice}`/

et `concreteFields.stockUnits`. `founderProspectionHoursAllocated` reste
un champ de `BusinessAction` à part entière (inchangé) — il alimente
maintenant `computeOfferDemand` (§5.1) au lieu de `deriveTargetValue`.

## 10. `Offer.lastDemand` (persisté, migration)

`Offer` (types/offer.ts) gagne `readonly lastDemand: DemandFunnelResult |
null` (défaut `null` — `createOffer`, offres en développement, et
`synthesizeLegacyOffer` en migration). Migration (`storage.ts`) : ajouter
`lastDemand: null` à `synthesizeLegacyOffer` ; pour toute offre déjà
persistée sans ce champ (sauvegardes M11.2.1), `offer.lastDemand ?? null`
lors du chargement — même discipline défensive qu'aux passes précédentes.
`targetSegment` reste une chaîne (aucun changement de type) : le web
propose désormais un **sélecteur** parmi les segments réels de la famille
(`getMarketSegments`) plutôt qu'un champ libre, mais une chaîne existante
qui ne correspond à aucun id de segment (sauvegarde migrée, ou l'ancienne
valeur libre « Clientèle existante ») ne casse rien — `computeSegmentFit`
n'applique simplement aucun bonus de ciblage principal dans ce cas
(dégradation silencieuse et sûre, jamais un crash).

## 13. Auto-revue

- *Un score unique de fit ?* — refusé explicitement par le brief ; conservé
  en 4 composantes + combinaison, toutes trois portées jusqu'à l'UI.
- *Segments état persisté ou catalogue statique ?* — tranché : catalogue
  statique pur (aucune migration nécessaire pour les segments eux-mêmes,
  seul `Offer.lastDemand` — un résultat, pas un paramètre — est persisté).
- *Tendance segment exponentielle sur date absolue ?* — rejetée (risque
  d'explosion/dépendance à l'année réelle) ; remplacée par une dérive
  linéaire sur l'ancienneté de l'offre (`monthsBetween(offer.createdAt,
  date)`), bornée et indépendante du calendrier réel.
- *Plusieurs offres, vraie allocation de portefeuille ?* — refusée
  explicitement par la consigne ; la boucle séquentielle à capacité
  partagée est la plus simple architecture qui rend chaque offre
  réellement attribuable sans construire un système de portefeuille.
- *Subscription sans plafond de capacité, est-ce une lacune ?* — non,
  c'est l'état réel du moteur `computeSubscriptionMonth` (vérifié à la
  lecture) ; documenté comme tel plutôt que masqué par un plafond
  fabriqué.
- *Infrastructure/emplacement comme canal de visibilité ?* — non ajouté :
  aucune donnée d'infrastructure n'a de signal de zone de chalandise
  exploitable proprement aujourd'hui ; documenté comme extension propre
  pour M11.3 (paramètre optionnel futur, pas une dette cachée).

## 14. Hors scope (rappel)

M11.2.3 (satisfaction/réachat), M11.2.4 (comptes stratégiques), M11.2.5
(concurrents individualisés), M11.2.6 (intelligence de marché complète),
M11.3 (marketing avancé). Pas de canal d'acquisition payant. Pas de
tarification par cohorte pour `subscription`. Pas de zone de chalandise
liée à l'infrastructure.
