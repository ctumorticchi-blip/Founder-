# FOUNDER — M11.1.5 « Constraints, Property & Ownership » — Plan d'implémentation

Réfère : `docs/superpowers/specs/2026-09-07-founder-m11.1.5-design.md`.
Amendement au plan `docs/superpowers/plans/2026-09-07-founder-m11-implementation.md`
(qui reste la référence pour M11.2-M11.5, non touchés ici).

Ordre d'implémentation choisi : **E → A → C → B → D**. Justification :
E et A sont les extensions moteur les plus petites et débloquent les
types que C réutilise (capacité, temps fondateur) ; C (portefeuille) est
la plus grosse refonte web mais ne dépend pas de B/D ; B (immobilier) et D
(valorisation/cession) sont les deux nouveaux modules moteur les plus
gros, indépendants l'un de l'autre, et s'appuient sur C pour leur UI.

## T1 — Moteur : temps fondateur explicite (fondation pour C et E)

Fichiers : `src/engine/simulation/types.ts`, `simulateMonth.ts`.

- `BusinessAction` gagne `founderProspectionHoursAllocated: number`
  (obligatoire) et `note?: string` (optionnel, passe-plat narratif).
- `validateActions` : `totalFounderHours` somme désormais
  `founderHoursAllocated + founderProspectionHoursAllocated` sur toutes
  les actions, toujours comparé à `timeAllocation.business` (garde
  existante étendue, pas remplacée).
- `simulateMonth` : si `action.note` est fourni, pousse un `GameEvent` de
  type `business-note` avec ce message tel quel.
- `types/narrative.ts` : `GameEventKind` gagne `business-note` (+ ajouté à
  `MEMORABLE_EVENT_KINDS` dans `narrative.ts`).

Tests : somme des heures fondateur incluant la prospection rejetée si elle
dépasse `timeAllocation.business` ; `note` produit bien un `GameEvent`
`business-note` avec le message fourni ; sans `note`, aucun événement
supplémentaire. Tous les littéraux `BusinessAction` existants (tests +
scénarios CLI) gagnent `founderProspectionHoursAllocated: 0`.

## T2 — Moteur : capacité d'infrastructure (A, §3.2)

Fichiers : `src/engine/simulation/types.ts`, `simulateMonth.ts`.

- `BusinessAction` gagne `headcountCapacity: number`,
  `storageCapacity: number` (obligatoires).
- `validateActions` : nouvelles vérifications (avant résolution) —
  `targetHeadcount > headcountCapacity` → `RangeError` avec message
  actionnable ; pour une action `decisions.family === "retail"`,
  `decisions.stockUnits > storageCapacity` → `RangeError` équivalent.
  Le message inclut l'effectif/stock actuel et la capacité, pour que le
  web puisse l'afficher tel quel (cohérent avec le pattern d'erreurs
  existant, remonté par `GameProvider::END_MONTH`).

Tests : recrutement au-delà de la capacité rejeté avec message contenant
la capacité ; recrutement à exactement la capacité accepté (borne
inclusive) ; stock retail au-delà de `storageCapacity` rejeté ; toutes les
familles non-retail ignorent `storageCapacity` (jamais de rejet
inattendu) ; tous les littéraux `BusinessAction` existants gagnent des
valeurs de capacité larges (ex. `Number.POSITIVE_INFINITY` ou une valeur
haute) pour ne pas casser les 234 tests moteur existants sans rapport avec
cette contrainte.

## T4 — Web : changement de locaux avec coût de déménagement (A, §3.3)

Fichiers : `web/src/state/types.ts` (+ `committedInfrastructureId` sur
`BusinessDraft`), `web/src/state/draft.ts` (`buildBusinessAction` facture
le `setupCost` si `infrastructureId !== committedInfrastructureId` ;
`deriveNextDraft` met à jour `committedInfrastructureId`),
`web/src/components/business/InfrastructurePicker.tsx` (confirmation
inline avant changement, hors création).

Tests : changer d'infrastructure sur une entreprise existante facture le
`setupCost` de la nouvelle option ce mois-ci ; le mois suivant, aucun
nouveau frais tant que l'infrastructure ne change plus ;
`committedInfrastructureId` suit bien l'infrastructure réellement
utilisée après résolution (pas la sélection en cours si le joueur change
d'avis avant fin de mois).

## T5 — Web : `MonthDraft.businesses` (portefeuille, C §5.1)

Fichiers : `web/src/state/types.ts`, `draft.ts`, `GameProvider.tsx`,
`lib/storage.ts` (migration).

- `MonthDraft.business` → `MonthDraft.businesses: readonly BusinessDraft[]`.
- `BusinessDraft` gagne `founderHoursAllocated`,
  `founderProspectionHoursAllocated`, `committedInfrastructureId`,
  `prospectionHours` (T7).
- `buildMonthActions` construit une `BusinessAction` par élément.
- `deriveNextDraft` traite chaque entreprise indépendamment (filtre celles
  disparues de `nextState.businesses` — liquidées ou vendues — remet
  `purchases: []`, etc., inchangé sinon).
- `draftValidationError` : somme des heures (production + prospection) de
  toutes les entreprises comparée à `timeAllocation.business`.
- `GameProvider` : `START_BUSINESS` ajoute au tableau au lieu de
  remplacer ; nouvelles actions pour cibler une entreprise précise
  (`UPDATE_DECISIONS`, `SET_MARKETING_BUDGET`, etc. gagnent un paramètre
  `businessId`).
- Migration `storage.ts` : `draft.business` singulier (M11.1) →
  `draft.businesses` tableau.

Tests : migration d'une sauvegarde M11.1 (`draft.business` singulier) sans
crash, `draft.businesses` contient bien l'entreprise migrée avec des
valeurs de capacité/temps par défaut cohérentes ; création d'une deuxième
entreprise ajoute au tableau sans perdre la première ; `buildMonthActions`
produit une `BusinessAction` par entreprise active ; validation rejette
une somme d'heures (production + prospection, toutes entreprises
confondues) dépassant le budget disponible.

## T8 — Moteur : immobilier professionnel (B)

Fichiers : nouveau `src/engine/business/realEstate.ts`,
`src/types/business.ts` (`BusinessState.properties`),
`businessResolution.ts` (intègre maintenance/intérêts/principal),
`simulation/types.ts` (`BusinessAction.propertyPurchase`).

Tests (TDD, avant l'intégration) : `computeMortgagePayment` conforme à la
formule d'amortissement standard (vérifiée sur un cas connu calculable à
la main) ; `evaluateFinancingEligibility` refuse si apport > cash
disponible, refuse si mensualité > seuil × EBITDA, refuse sans
`lastStatement` (entreprise trop jeune), accepte sinon avec message clair
en cas de refus ; `applyMortgagePayment` répartit intérêts/principal
correctement sur plusieurs mois consécutifs (le principal restant dû
décroît, jamais négatif) ; `purchaseProperty` déduit l'apport du cash et
ajoute l'actif à `properties` ; intégration `resolveBusinessMonth` — la
maintenance de tous les biens possédés s'ajoute à `admin`, les intérêts
immobiliers à `interest`, le principal remboursé réduit le cash sans
apparaître en charge P&L.

## T9 — Web : catalogue et flux d'achat immobilier (B §4.4)

Fichiers : nouveau `web/src/data/realEstate.ts`, nouveau composant
`web/src/components/business/PropertyPurchasePanel.tsx`, wiré dans
`BusinessScreen.tsx` (replié par défaut, masqué si infrastructure active
= Domicile), `FinancesScreen.tsx` (lignes maintenance/mensualité/principal
restant dû, défensives pour sauvegardes sans biens).

Tests : le panneau n'apparaît pas pour une entreprise à domicile ; achat
réussi diminue le cash entreprise (et le cash personnel si apport
personnel) du montant de l'apport ; achat refusé affiche le message
d'explication renvoyé par le moteur ; le bien acheté persiste dans
`FinancesScreen` après plusieurs mois et un reload (sauvegarde/chargement).

## T10 — Moteur : valorisation (D §6.1)

Fichier : nouveau `src/engine/business/valuation.ts`.

Tests (TDD) : `computeValuation` déterministe (même entrée → même sortie,
testé explicitement) ; multiple plus élevé pour `subscription` que pour
`retail` à EBITDA égal ; décote de valorisation quand
`unpaidObligations > 0` ou `isInsolvent` ; `factors` somme cohérente avec
`mid` (traçabilité) ; `low <= mid <= high` toujours vérifié, y compris cas
limites (EBITDA négatif, trésorerie négative-nette).

## T11 — Moteur : processus de cession (D §6.2)

Fichiers : nouveau `src/engine/business/sale.ts`, `simulation/types.ts`
(`OwnedBusiness.saleProcess`, `BusinessAction.saleDecision`),
`simulateMonth.ts` (nouvelle étape : avancer les processus de cession en
cours, traiter les décisions du joueur, clôturer si acceptée).

Tests (TDD, critiques pour la DoD) : même seed → même déroulé du
processus de vente (déterminisme, testé sur plusieurs mois consécutifs) ;
une société de très mauvaise qualité (`isInsolvent` proche, EBITDA très
négatif) peut ne recevoir aucune offre sur la durée testée (« société
invendable possible ») ; l'acceptation d'une offre calcule le produit net
correctement (offre − dettes − frais de transaction) et l'ajoute à
`character.cash` ; la société vendue disparaît de `GameState.businesses`
dès le mois de clôture ; un `GameEvent`/`MemoryEntry` de type
`business-sold` est produit avec le montant net ; refuser/retirer une
offre ne clôture rien et n'affecte pas la trésorerie ; une contre-offre
trop agressive peut échouer (règle simple documentée en spec §6.2).

## T12 — Web : UI de cession (D §6.3)

Fichiers : nouveau `web/src/components/business/SalePanel.tsx`, wiré dans
`BusinessScreen.tsx`/`PortfolioScreen.tsx`, `NewsScreen.tsx`/
`MonthRecapModal.tsx` (afficher l'événement `business-sold`).

Tests (RTL) : mise en vente déclenche l'affichage du statut de processus ;
une offre reçue affiche Accepter/Refuser/Contre-offrir ; accepter une
offre retire l'entreprise du portefeuille et affiche un événement de
cession avec le montant ; « Pourquoi cette entreprise vaut environ X ? »
affiche les facteurs de `ValuationResult`.

## T13 — Validation complète, playtest, commit

- `npm test`, `npm run typecheck`, `npm run typecheck:test`, `npm run lint`
  (racine, moteur).
- `cd web && npm test && npm run typecheck && npm run lint && npm run build`.
- Playtest Playwright (iPhone 13) couvrant le parcours complet du brief
  §I : créer entreprise → recruter jusqu'à capacité → tentative de
  recrutement bloquée avec message → agrandir les locaux → recruter avec
  succès → créer une deuxième entreprise → répartir le temps fondateur
  (impossible de tout allouer aux deux) → mettre la première en vente →
  recevoir/refuser ou accepter une offre → continuer à jouer.
- Commit + push sur `main` uniquement une fois tout vert.
