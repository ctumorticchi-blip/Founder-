Pas de test dédié (types), couvert par la compilation stricte + T2/T3.

#### T2 — Moteur : `engine/business/offer.ts` (TDD)

Fichier (nouveau) : `src/engine/business/offer.ts`.
Tests (nouveau) : `test/engine/business/offer.test.ts`, écrits en premier.

- `computeLaunchThreshold(businessModel)` — table fixe (spec §3.2).
- `createOffer(spec, date)` — rejette nom vide/blanc (`RangeError`), prix
  négatif ; retourne une offre `status: "in-development"`, `maturity: 0`,
  `qualityLevel: INITIAL_QUALITY_LEVEL`, cumuls investis à 0,
  `launchedAt: null`.
- `developOffer(offer, hours, budget)` — rejette `hours < 0`/`budget < 0` ;
  incrémente `maturity` (clamp [0,100]) si `in-development`, `qualityLevel`
  (clamp [0,100]) si `launched` ; accumule les cumuls investis ; **aucun
  RNG** (déterminisme trivial, vérifié par un test "deux appels identiques
  produisent le même résultat").
- `launchOffer(offer, date)` — rejette si déjà lancée, rejette si
  `maturity < computeLaunchThreshold(offer.businessModel)` avec un message
  actionnable citant `offer.name` (jamais `offer.id`) et le seuil requis ;
  accepte `service-hours` à `maturity: 0`.
- `updateOfferPricing(offer, price, positioning)` — rejette prix négatif.

Tests couvrant explicitement, avec valeurs chiffrées correspondant au
scénario calibré spec §3.2 (20 h + 500 € ⇒ 40 points/mois) :
- progression multi-mois (3 appels `developOffer` successifs sur la même
  offre, vérifier l'accumulation) ;
- lancement bloqué pour `unit-sale`/`recurring`/`project` en dessous du
  seuil, débloqué au-dessus ;
- lancement immédiat pour `service-hours` sans aucun développement ;
- amélioration post-lancement : `developOffer` sur une offre `launched`
  n'incrémente plus `maturity`, incrémente `qualityLevel`.

#### T3 — Moteur : intégration `resolveBusinessMonth`/`simulateMonth`

Fichiers : `src/engine/simulation/businessResolution.ts`,
`src/engine/simulation/simulateMonth.ts`, `src/types/business.ts`
(+`offers: readonly Offer[]`), `src/engine/simulation/types.ts`
(+`BusinessAction.offerActions?`).

- `BusinessState.offers` : défaut `[]`, initialisé par
  `createOwnedBusiness`/`createBusiness` (même précédent que `properties`).
- `businessResolution.ts` : nouvelle fonction privée `applyOfferActions`
  (spec §3.3) appliquant `create`/`develop`/`launch`/`update-pricing` dans
  l'ordre du tableau, retournant `{offers, developmentSpend}` ; le
  `developmentSpend` rejoint la ligne `admin` du `computeMonthlyFinancials`
  déjà appelée (même bucket que la maintenance immobilière, aucun nouveau
  champ de statement).
- `simulateMonth.ts::validateActions` : étend la somme des heures
  fondateur (déjà `founderHoursAllocated + founderProspectionHoursAllocated`)
  pour inclure `Σ(action.offerActions "develop".hours)`, contre le même
  `timeAllocation.business`.

Tests (TDD, `test/engine/simulation/offerIntegration.test.ts`, écrits avant
le code d'intégration) :
- une action `develop` réduit l'EBITDA/le cash du montant du budget investi
  ce mois-ci (vérifié sur le `statement` retourné) ;
- une action `develop` dont les heures dépassent le temps "business"
  restant (déjà utilisé par production+prospection) est rejetée par
  `simulateMonth` (`RangeError`), mois atomique (rien n'est appliqué) ;
- une action `launch` prématurée lève une `RangeError` dont le message ne
  contient jamais `offer.id`, uniquement `offer.name` ;
- deux offres sur une même entreprise progressent indépendamment le même
  mois (deux actions `develop` dans le même `offerActions`) ;
- deux entreprises différentes du portefeuille développent chacune leur
  offre le même mois sans interférence (garde de non-régression multi-
  entreprises, cf. précédent M11.1.5) ;
- progression sur plusieurs mois consécutifs (3 appels `simulateMonth`
  successifs) accumule `maturity` de façon cohérente et déterministe ;
- même seed + mêmes actions ⇒ même état d'offre produit (déterminisme,
  garde `test/guards/forbiddenApis.test.ts` déjà verte, pas de nouveau
  `Math.random`/`new Date()` introduit).

#### T8 — Web : `draft.ts` (`buildBusinessAction`, `deriveNextDraft`)

Fichier : `web/src/state/draft.ts`.

- `buildBusinessAction(b, gameState)` : calcule `activeOfferPrice` en
  lisant `gameState.businesses[].business.offers`, trouve la première
  offre `status === "launched"` (spec §3.4), l'injecte dans
  `deriveDecisions(...)` ; inclut `b.offerActions` dans
  `BusinessAction.offerActions` si non vide.
- `deriveNextDraft` : reset `offerActions: []` chaque mois (même motif que
  `purchases`/`propertyPurchase`/`saleDecision`).
- `totalFounderBusinessHours`/`draftValidationError` : étendus pour inclure
  la somme des heures `develop` de `offerActions` dans le total comparé à
  `timeAllocation.business` (garde web, doublée par le moteur — même
  discipline que M11.1.5 §5.1).

Tests (TDD, `web/test/draft.test.ts`) :
- une entreprise avec une offre lancée en `gameState` produit
  `BusinessAction.decisions.price` égal au prix de cette offre ;
- aucune offre lancée ⇒ prix `0` ;
- deux offres lancées ⇒ la première par ordre de création détermine le
  prix (règle déterministe, spec §3.4) ;
- `offerActions` non vide est correctement inclus dans l'action construite ;
- `deriveNextDraft` vide `offerActions` après résolution ;
- `draftValidationError` rejette une allocation dépassant le budget une
  fois les heures de développement comptées.

#### T10 — Web : migration de sauvegarde

- `migrateSaveGame` étendu (spec §3.7) :

- `draft.businesses[i].offerActions` défaut `[]` si absent.

Tests (TDD, `web/test/storageMigration.test.ts`) :
- une sauvegarde M11.1.5 (sans `offers`) migre sans exception, obtient une

- idempotence : migrer deux fois produit le même résultat (id stable) ;
- ne modifie aucune valeur `gameState` existante hors complétion de champ
  manquant (même test que M11.1.5, étendu à `offers`).

#### T11 — Web : écrans

Fichiers (nouveaux) : `web/src/screens/{CreateOfferScreen,OfferScreen}.tsx`,
`web/src/components/business/OffersCard.tsx`. Fichiers modifiés :
`web/src/state/Navigation.tsx` (+2 routes), `web/src/components/layout/
AppShell.tsx` (+2 cas), `web/src/screens/BusinessScreen.tsx` (+`OffersCard`),
`web/src/components/business/DecisionFields.tsx` (retire les champs prix).

- `CreateOfferScreen` : formulaire complet (nom, modèle économique filtré
  par famille, positionnement, cible, prix pré-rempli, temps & budget de
  développement du premier mois) ; soumission ajoute `create`
  (+ `develop` si > 0) à `draft.businesses[i].offerActions` ; navigue vers
  `BusinessScreen`.
- `OfferScreen` : lit l'offre réelle depuis `gameState` (jamais depuis le
  draft pour son état persistant) ; barre de maturité + seuil si en
  développement ; bouton « Lancer » (désactivé + explication sous le
  seuil) ; barre de qualité + panneau développement si lancée ; prix/
  positionnement éditables (`update-pricing`).
- `OffersCard` (dans `BusinessScreen`) : liste compacte + « + Nouvelle
  offre » ; message d'invitation si aucune offre.
- `DecisionFields` : retire `price`/`averageTicketPrice`/`unitPrice` ;
  garde `retail.stockUnits` ; message informatif si aucune offre lancée.

Tests (RTL, TDD, `web/test/offerFlow.test.tsx`) :
- créer une offre, investir sur 2-3 mois, vérifier la progression affichée
  de la maturité ;
- tenter de lancer avant le seuil → bouton désactivé/message explicite ;
  lancer après le seuil → succès, statut affiché change ;
- modifier prix/positionnement après lancement → répercuté à l'écran et
  dans `FinancesScreen` au mois suivant ;
- améliorer après lancement → progression de la qualité affichée ;
- aucun id technique (`offer.id`) visible dans le DOM à aucune étape
  (assertion négative, même invariant I1 que M11.1) ;
- coexistence : créer une deuxième offre sur la même entreprise sans
  perdre la première ; une deuxième entreprise du portefeuille a ses
  propres offres indépendantes.

#### T13 — Playtest mobile (Playwright, iPhone 13)

Depuis une **nouvelle partie** (pas de save seedée par script sauf pour les
tests de migration dédiés, spec T10) : créer un entrepreneur (onboarding
existant) → créer une entreprise (flux `CreateBusinessScreen` existant,
inchangé) → construire une offre (`CreateOfferScreen`) → investir plusieurs
mois (temps + budget de développement, plusieurs `simulateMonth`) → lancer
l'offre → modifier prix/positionnement → améliorer l'offre (post-lancement)
→ recharger la page (persistance) → continuer plusieurs mois. Rechercher
activement les incohérences UX (messages peu clairs, boutons ambigus,
sélecteurs conflictuels — cf. leçons du playtest M11.1.5) et les corriger
avant de considérer la tâche terminée.
