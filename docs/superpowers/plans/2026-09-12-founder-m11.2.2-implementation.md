## Tâches (TDD strict : tests écrits avant le code de chaque module)

### T1 — Types : `CustomerSegment`, `FitBreakdown`, `DemandFunnelResult`
`src/types/customerSegment.ts`, `src/types/demand.ts` (nouveaux).

### T2 — Catalogue de segments (TDD)
`src/engine/market/segments.ts` + `test/engine/market/segments.test.ts` :
4 segments/famille, `relativeSize` sommant à 1, seasonality/referencePrice
variés. Tests : 3-5 segments par famille (les 5 familles), somme
`relativeSize` ≈ 1, chaque segment a un id unique par famille, aucune
valeur hors bornes (0-1 pour les ratios, 0-100 pour qualityExpectation).

### T3 — Product-Market Fit (TDD)
`src/engine/market/demand.ts::computeSegmentFit` +
`test/engine/market/demand.test.ts` (créé ici, étendu en T4) : sensibilité
prix différente par segment, sensibilité qualité différente, influence du
positionnement, influence de la réputation, bonus de ciblage principal
(sans exclusivité — un segment secondaire peut rester dominant),
déterminisme (mêmes entrées ⇒ mêmes sorties, aucun RNG).

### T4 — Entonnoir de demande (TDD)
`computeOfferDemand` (même fichier). Tests : marché → disponibilité
(tendance via ancienneté d'offre, saisonnalité, conjoncture déjà portée
par `market.sizeMonthlyRevenuePotential`) ; entonnoir complet
(availableMarket ≥ reached ≥ interested, demand cohérent) ; faible
visibilité malgré excellente offre (prospection nulle + réputation basse
→ reached faible malgré fit élevé) ; mauvaise offre malgré forte
visibilité (prospection élevée + réputation haute mais fit faible →
interested faible) ; bucketage `visibilityLevel`/`priceSignal`/
`demandSignal` cohérent avec les grandeurs sous-jacentes ; aucune fuite de
coefficient brut dans le résultat public (vérifié en TypeScript par la
forme du type + un test qui énumère les clés de l'objet retourné).

### T5 — Intégration `resolveBusinessMonth` (TDD, cœur de la vérification)
`src/engine/simulation/businessResolution.ts` réécrit par famille (spec
§6) ; `src/engine/simulation/simulateMonth.ts` passe `markets[owned.marketId]`
en 7ᵉ argument. `src/types/business.ts` inchangé. `src/types/offer.ts` :
+`lastDemand`. `src/engine/simulation/types.ts` : `BusinessFamilyDecisions`
simplifié (spec §9).

Tests (`test/engine/simulation/demandIntegration.test.ts`, nouveau) :
- demande < capacité (sales = demand, lostToCapacity = 0) ;
- demande > capacité (sales = capacity-bound, lostToCapacity > 0) ;
- deux offres sur la même entreprise : capacité partagée séquentiellement,
  chaque offre a son propre `lastDemand` (coexistence, attribution) ;
- deux entreprises différentes : indépendance totale ;
- les 5 familles produisent un `lastDemand` cohérent après lancement d'une
  offre adaptée ;
- Agency : `offer.price` (pas `state.averageMonthlyFeePerMandate`) pilote
  réellement le revenu — test qui change uniquement `offer.price` entre
  deux mois et observe un revenu différent ;
- Subscription : `offer.price` pilote `arpu` effectif, `lastDemand.capacity
  === Infinity`, `lostToCapacity === 0` ;
- sans offre lancée : revenu nul, comportement M11.2.1 préservé ;
- déterminisme : même seed + mêmes actions ⇒ même `lastDemand` sur
  plusieurs mois consécutifs ;
- **preuve négative explicite** : deux mois avec la même
  `founderProspectionHoursAllocated`/capacité mais des offres de prix très
  différents produisent des revenus différents dans un rapport cohérent
  avec le rapport des prix × ventes — le CA suit la vente réelle, pas un
  simple multiplicateur de temps de prospection.

Bulk-fix mécanique (retrait des champs supprimés de §9, ajout du 7ᵉ
paramètre `market` aux appels directs de `resolveBusinessMonth`) dans les
fixtures des tests existants : `test/engine/simulation/{businessResolution,
capacityConstraints,capitalInjection,realEstateIntegration,
retailAgencyOrchestration,saleIntegration,simulateMonth,offerIntegration}.test.ts`,
`test/scenarios/{multiBusiness,trajectory}.test.ts`,
`src/scenarios/{service,hospitality,subscription}.ts`. Là où un test a
besoin d'une demande garantie (ex. « capacity-bound »), construire une
offre déjà lancée avec un prix/qualité cohérents plutôt que manipuler un
champ `targetHours` qui n'existe plus — **jamais** contourner en assouplissant
l'assertion sans comprendre le nouveau mécanisme.
